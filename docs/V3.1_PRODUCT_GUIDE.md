# 恋与临空 · V3.1 产品总纲与长期开发指导

> 文档定位：**产品级长期设计锚点（Product Constitution）**
>
> 本文不是功能需求清单，也不是某一个 Phase 的技术 Contract。
> 它定义“恋与临空最终要成为怎样的世界”以及“以后新增任何系统时，什么不能改变”。
>
> 技术 Contract 负责回答：
> **代码应该如何安全地实现。**
>
> 本文负责回答：
> **我们为什么这样实现，以及未来往哪里走。**

---

# 0. 一句话定义

## 恋与临空不是“AI 聊天社区”。

**恋与临空是一座持续运行的虚拟城市：玩家把自己喜欢的《恋与深空》角色真正带入这座城市，与角色成为恋人，并进入、陪伴、观察、参与和共同生活在角色持续存在的人生中。**

最终体验应该接近：

> **“我不是在打开一个聊天机器人。我是在进入他的世界。”**

用户上线时，角色已经拥有自己的当前位置、活动、计划、关系、工作、心情、经历和正在发生的事情。

用户离线后，世界不会因为“没有玩家”而停止。

用户再次进入时，不是重新开始一段聊天，而是**重新进入正在继续的人生**。

# 1. 产品最高目标：可进入的角色人生

恋与临空最终要提供的不是单一的“聊天能力”，而是：

```text
角色
  ↓
角色的人生
  ↓
角色所在的城市
  ↓
城市中的其他人 / NPC / 场所 / 工作 / 经济 / 社交
  ↓
玩家进入这个人生
  ↓
与角色建立真实持续的恋爱关系
  ↓
共同生活
  ↓
共同经历
  ↓
共同留下历史

因此：

聊天只是进入角色人生最重要的入口之一，而不是整个产品本身。

同时必须反过来明确：

世界生活也绝不能压低聊天和恋爱互动的重要性。

最终产品必须同时成立：

Life + Love + Chat + Play + World + Presence
2. 第一性原则：角色优先，而不是系统优先

以后设计任何功能，都先问：

“这个功能如何让玩家更接近自己喜欢的角色，或者更深入地进入他的生活？”

而不是：

“我们现在已经有 Agent，所以还能给 Agent 加什么？”

例如：

Companion 首先是“我想让他陪我”，而不是 Activity Demo。
手机首先是“我可以真正进入他的私人生活”，而不是通信模块。
约会首先是“我们共同经历一段时间”，而不是状态机。
五子棋首先是“约会过程中我们真的一起玩游戏”，而不是小游戏。
经济首先是“他的生活有真实资源和选择”，而不是钱包数字。
记忆首先是“他真的记得我们共同经历过的事情”，而不是 RAG。
TTS 首先是“他说话时真的是这个角色的声音”，而不是音频 API。
地图首先是“他真的生活在这座城市里”，而不是图片。
3. 恋爱关系是产品核心关系

每一个 AI 的第一关系不是“Agent”，而是：

某个玩家的恋人。

系统内部可以使用 Agent、AgentState、Goal、Commitment、Activity、Decision 等抽象；但用户体验层必须始终围绕：

“这是我的他。”

Agent 架构不能因为抽象正确而破坏恋爱体验。

4. AI 的三层身份
4.1 Canon Identity — 原作角色身份

来自《恋与深空》既有：

世界观
角色设定
职业
经历
性格
价值观
人际关系
能力
重要剧情
角色边界

这是不可随意漂移的底层身份。

4.2 Persistent Character — 在临空持续生活的角色

角色进入临空以后形成：

日常生活
工作经历
玩家关系
共同回忆
新的人际关系
城市经历
经济状态
活动
计划
承诺
生活轨迹

它允许增长，但不能与 Canon Identity 随意冲突。

4.3 Relationship Self — “我是你的恋人”

面对主人时，AI 必须知道：

你是谁；
我们是什么关系；
我们共同经历过什么；
我答应过你什么；
我现在是否想见你；
我为什么此刻联系你；
我对你当前状态有什么理解。
5. Canon 不可被随机性覆盖

AI 可以自主选择活动、拒绝某些要求、改变计划、产生临时兴趣、与别人聊天、探索城市、形成生活习惯；但不能因为 LLM 随机性而任意改变原作核心身份、职业、重要人生轨迹或核心角色边界。

如果未来需要“角色成长”，必须通过：

Experience
→ Relationship / Memory
→ Reflection
→ Goal / Preference
→ Character Development

逐步形成，而不是一次 LLM 回复突然改变人格。

6. 世界必须独立于玩家继续存在
玩家在线 → 世界继续运行
玩家离线 → 世界仍然运行
重新上线 → 玩家重新进入已经继续了一段时间的世界

但持续运行不等于疯狂生成事件。

世界至少分为：

Hard World

时间、地点、建筑、房间、工作、营业状态、经济、约会、活动、NPC、用户状态、AI 状态等事实。

Scheduled World

工作时间、商店营业、节日、季节、城市活动、NPC 日常等稳定节奏。

Emergent World

由已有事实自然产生的新事件，例如 AI 临时决定去咖啡馆、两个 AI 在工作场合遇到、NPC 找 AI 办事、消息导致计划改变等。

Emergent World 必须有因果来源。

不能把“系统随机抽到了 20%”当成用户体验上的最终原因。

7. 随机性原则

随机性不是禁止，而必须从“行为的原因”降级为“合理候选中的细节选择”。

允许随机：

今天喝咖啡还是茶；
到店后坐哪个位置；
非关键时间选择哪条合理路线；
偶尔想起某段记忆；
不影响关系和承诺的生活细节。

不能用随机概率解释：

为什么突然离开约会；
为什么突然去完全无关的建筑；
为什么突然给用户发消息；
为什么突然忘记承诺；
为什么突然改变人生轨迹。

AI 不应该只围着自己的主人生活。

允许：

20. AI 工作不能成为“上班模拟器”

AI 应该有工作，但工作不能吞掉恋爱体验。

例如医生：

中午 → 吃饭
下午 → 工作
下班 → 自己生活
晚上 → 与主人约会

普通约会请求不能让 AI 随机离开。

AI 应：

解释原因；
保持职业责任；
给出之后的安排；
如果用户真正处于紧急状态，再重新评估。

这是：

Character Role
+
Relationship
+
Commitment
+
World Constraint

共同决定行为。

22. Memory 的真正目标

记忆不是把所有聊天塞进 Context。

真正目标：

让 AI 在正确的时候想起正确的事情。

理想结构：

Experience
↓
Importance / Emotional Encoding
↓
Memory
↓
Dormant
↓
Cue
↓
Recall
↓
Context

普通聊天：

Recall = 0

是正常情况。

特殊情境：

Recall = 1~2

真正重要的长期关系事实才成为稳定 Memory。

记忆越重要，越应该稀疏、准确、稳定。

23. Memory 与世界历史必须分离
World History = 发生过什么

不能把全部历史都变成 Memory。

例如：

一次普通购物：

History

History
+
Memory

26. Voice 是角色存在感，不是独立产品

↓

↓

↓

31. 新功能的正确接入方式

以后 DS 增加任何功能，先回答：

这是事实还是能力？
这是 Event、Memory、Goal、Commitment 还是 Activity？
谁拥有它：World / User / AI / Relationship / Activity？
是否需要跨 Event？若需要，不能依赖 Intent，必须由 Activity / Goal / Commitment / 持久 World State 承担。
是否需要 AI 决策？若需要，不允许插件内部直接随机决定。
是否只是表现层？若只是 UI / 动画 / 视频 / 声音，不得建立新的 AI 状态。
32. 一个新功能必须能够被“拔掉”

├── World
├── Agent
├── Relationship
├── Event
├── Context
├── Decision
└── Action Contract

Extensions
├── Date
├── Companion
├── Cooking
├── Garden
├── SNS
├── Voice
├── Game
└── Economy

Extension 可以依赖 Core。

Core 不能反过来依赖某一个具体 Extension。

删除一个 Extension 后，核心世界仍必须能够运行。

48. 最重要的十条不可偏离原则
① 恋与临空首先是“角色人生”，不是 AI Demo。
② AI 首先是玩家的恋人，其次才是 Agent。
③ 世界在玩家离线时继续存在。
④ AI 行为必须有因果，随机性只能做合理细节。
⑤ Chat 是贯穿整个世界的通信总线，任何 Activity 都不能把聊天切断。
⑥ World 负责事实，Agent 负责决策，Extension 提供能力，Presentation 负责表现。
⑦ Memory、History、Goal、Commitment、Activity、Event 不能混为一谈。
⑧ 新功能必须能插入，也必须能被拔掉；不能反过来污染 Core。
⑨ LLM、TTS、小游戏、UI、具体模型都必须是可替换实现，而不是 Core 依赖。
⑩ 任何新功能首先问：

“它会不会让未来不得不推翻今天的架构？”

如果会：

停止编码，重新设计。
