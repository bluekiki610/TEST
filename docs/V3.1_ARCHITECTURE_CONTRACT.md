## 0. 总原则

V3.1 = orchestration / control layer over existing Linkong capabilities

≠ 重写 Linkong
≠ 建立第二套 World
≠ 建立第二套 Source of Truth

**改造策略**：
- 先统一语义，再拆文件
- 先接管决策，再迁移执行
- 先并行观察，再逐步切换
- 旧功能不能坏

## 1. Source of Truth

### 冻结规则

| 规则 | 内容 |
|------|------|
| **SOT-1** | `main.data` 是当前唯一 Source of Truth |
| **SOT-2** | AgentState 是 Projection，**不是** Source of Truth |
| **SOT-3** | Event 是"事实描述"，**不是** Source of Truth |
| **SOT-4** | 不允许任何 V3.1 模块创建第二数据源 |
| **SOT-5** | 不允许任何 V3.1 模块双向同步 `main.data` |
| **SOT-6** | 任何"缓存"必须是只读投影或可重建 |
| **SOT-7** | **【CC-20260927-01】** `main.data` 始终是 V3.1 唯一 Source of Truth |
| **SOT-8** | **【CC-20260927-01】** Goal / Commitment 不是 `main.data` 的子结构，也不是第二 Source of Truth |
| **SOT-9** | **【CC-20260927-01】** Goal / Commitment 不得与 `main.data` 双向同步 |
| **SOT-10** | **【CC-20260927-01】** Goal / Commitment 可以在未来拥有自己的持久化机制，但该机制**不得**产生第二个与 `main.data` 平行、同等权威的事实源。持久化介质必须在权威性上从属于 `main.data`，或被设计为可从 `main.data` 重建的只读投影。**不允许出现两个独立、平等、相互同步的 Source of Truth。** |
| **SOT-11** | **【CC-20260927-01】** 具体实现方案（独立 JSON / SQLite / 内存 + 快照 / 其他）未冻结；最终权威性、重建关系、一致性边界未冻结；留待后续 Contract Change |

## 4. AgentRuntime

### 定义
单个 AI 的 orchestration 生命周期。

### 生命周期
```text
RECEIVE → PERCEIVE → WAKE_DECISION → CONTEXT
→ THINK → DECISION → ACTION → WORLD_CHANGE → EVENT
```

### 冻结规则

| 规则 | 内容 |
|------|------|
| **AR-1** | 一个 AI 一个 Runtime 实例（不是"超级 Runtime 管理所有 AI"） |
| **AR-2** | Runtime 不直接访问 `main.data`（只通过 Contract 方法） |
| **AR-3** | Runtime 不直接修改 World（只通过 Decision → Action 让现有 `ext_*` 修改） |
| **AR-4** | Runtime 不替代 `ext_ai`（**旁路观察**） |
| **AR-5** | P0-3B 感知链保持不变 |
| **AR-6** | P0-3B **不返回 THINK**（留给未来 Wake Score） |
| **AR-7** | Runtime 不成为 `main.data` 第二个数据库 |
| **AR-8** | **【CC-20260926-01】** Runtime 的 CONTEXT 阶段输出类型冻结为 `AgentContext`（见 §5），不再返回 `ContextLayers` |
| **AR-9** | **【CC-20260926-01】** Runtime 的 THINK 阶段输入类型冻结为 `AgentContext`，不再接收 `ContextLayers` |
| **AR-10** | **【CC-20260926-01】** Runtime 不得同时调用旧 `ext_ai.build_ai_context` 与新 `ContextAssembler` |

### Context 阶段正式接口（CC-20260926-01 冻结）

```python
def build_context(
    self,
    event: Event,
    now_ts: Optional[float] = None,
) -> AgentContext:
    ...

def think(self, context: AgentContext) -> Optional[str]:
    ...
```

> 注：`think() -> Optional[str]` 是 B5 阶段的临时占位 / 兼容接口，
> **不代表最终 Intent Contract**。最终 Intent 数据结构见 §5A.4，
> 具体 schema 留待后续 Contract Change 冻结。

### 数据来源冻结（CC-20260926-01）

| 参数 | 提供者 | 方式 |
|------|--------|------|
| `ai_name` | Runtime | `self.ai_name` |
| `owner` | Runtime | `get_state().owner` |
| `data` | Runtime | `self._data`（不透明引用） |
| `now_ts` | 调用方注入 | 缺省由 `ContextAssembler` 使用当前时间 |
| `agent_state_dict` | Runtime | `get_state().to_dict()` |
| `recall_query` | Runtime | 固定 `None`（本阶段） |

## 5. Context Assembly

### 定义
独立于旧 `build_ai_context` 的 Context 构造层。

### 正式 Context 标准（CC-20260926-01）

**V3.1 唯一正式 Context 数据结构 = `AgentContext`（`agent/context.py`）。**

```text
Event
  ↓
RECEIVE
  ↓
PERCEIVE
  ↓
WAKE_DECISION
  ↓
CONTEXT
  ↓
AgentRuntime.build_context()
  ↓
ContextAssembler
  ↓
AgentContext
  ↓
THINK（仍为 Stub）
```

该数据链为 V3.1 唯一正式 Context 数据链。

### 分层
| 层 | 内容 | 是否增长 |
|----|------|---------|
| **A. Stable Core** | 世界观 / 人设 / 核心用户信息 / 长期身份 | ❌ 稳定 |
| **B. Recent** | 当前对话 / 最近 Event / 当前活动 | ❌ 有界 |
| **C. Long-term** | Memory / Relationship / 历史事件 | ✅ 按需检索 |
| **D. Dynamic World** | AgentState / 当前地点 / 当前世界状态 | ❌ 瞬时 |

### 冻结规则

| 规则 | 内容 |
|------|------|
| **CA-1** | Context Assembly 与旧 `build_ai_context` **并行运行** |
| **CA-2** | 不修改旧 `build_ai_context` |
| **CA-3** | 目标：历史增长**不**导致单次 Context 线性增长 |
| **CA-4** | 不粗暴砍掉现有 7k-10k tokens（保护世界观 / 人设 / 关系 / Memory 连续性） |
| **CA-5** | Long-term 层必须**按需检索**，不默认全量注入 |
| **CA-6** | **【CC-20260926-01】** `AgentContext` 是 V3.1 唯一正式 Context 数据结构，禁止新建平行 Context 结构 |
| **CA-7** | **【CC-20260926-01】** `ContextLayers`（P0-3A）正式 **deprecated**，保留兼容 stub，不删除、不改名、不别名化；新 V3.1 链不再引用它 |
| **CA-8** | **【CC-20260926-01】** 不允许长期存在"双 Context"：旧 `build_ai_context` 与新 `ContextAssembler` 不得在同一 AI 决策周期内同时触发 |
| **CA-9** | **【CC-20260926-01】** `ContextAssembler` 只能被 `AgentRuntime.build_context()` 调用；其他调用方需 Contract 变更 |
| **CA-10** | **【CC-20260926-01】** `decision_constraints` 当前保持 `None`，不得提前实现 Goal / Motivation / Commitment |

### ContextLayers 兼容状态（CC-20260926-01）

- `ContextLayers` 定义保留在 `agent/runtime.py`。
- 语义：**deprecated compatibility stub**。
- 不允许：
  - 删除；

  - 别名化（如 `ContextLayers = AgentContext`）；

### 5A.1 Goal

#### 定义

> **Goal = 我想完成什么。**

#### 生命周期（冻结）

```text
CREATED → ACTIVE → COMPLETED
              │
              ├──→ CANCELLED
              │
              └──→ EXPIRED
```

| 状态 | 含义 | 是否终态 |
|------|------|---------|
| `CREATED` | 刚被创建，未激活 | 否 |
| `ACTIVE` | 正在追求 | 否 |
| `COMPLETED` | 已达成 | 是 |
| `CANCELLED` | 主动取消 | 是 |
| `EXPIRED` | 被动过期 | 是 |

#### 冻结规则

| 规则 | 内容 |
|------|------|
| **GO-1** | 本阶段**不实现** Goal |
| **GO-2** | Goal 状态转换**单向**，不允许 `COMPLETED → ACTIVE` |
| **GO-3** | Goal 状态转换必须**可审计**（记录 reason） |
| **GO-4** | Goal 状态转换**不直接修改 `main.data`** |
| **GO-5** | Goal 允许多个同时存在 |
| **GO-6** | Goal 来源仅限：用户要求 / Commitment / Relationship / Memory / 未完成 Activity / 工作日程世界约束 / AI 自身长期偏好 |
| **GO-7** | Goal **禁止**凭空生成 |
| **GO-8** | Goal **禁止**随机生成 |
| **GO-9** | Goal **禁止**由未经验证的 LLM 输出直接生成 |
| **GO-10** | AI 必须未来能够拥有**不来自用户要求**的生活目标 |
| **GO-11** | Goal 必须能够**跨 Event 持续存在**；单个 Event 不得让 Goal 无故消失 |
| **GO-12** | Goal 优先级算法、冲突解决规则**未冻结**，留待后续 Contract Change |
| **GO-13** | Goal **最终持久化位置未冻结**（见 §5A.5） |

### 5A.2 Commitment

#### 定义

> **Commitment = 我已经答应 / 约定 / 承诺什么。**

#### 生命周期（冻结）

```text
CREATED → ACTIVE → FULFILLED
              │
              ├──→ CANCELLED
              │
              └──→ EXPIRED
```

| 状态 | 含义 | 是否终态 |
|------|------|---------|
| `CREATED` | 刚形成 | 否 |
| `ACTIVE` | 有效 | 否 |
| `FULFILLED` | 已兑现 | 是 |
| `CANCELLED` | 已取消 | 是 |
| `EXPIRED` | 已过期 | 是 |

#### 四类承诺（冻结）

| 类型 | actor | counterparty | 默认强度 |
|------|-------|--------------|---------|
| AI → 用户 | AI | 用户 | `hard` |
| 用户 → AI | 用户 | AI | `hard` |
| AI → AI | AI A | AI B | `soft` |
| AI 对自己 | AI | 自己 | `soft` |

#### 强度分级（冻结）

| 强度 | 含义 |
|------|------|
| `hard` | 明确承诺 |
| `soft` | 模糊承诺 |
| `implicit` | 隐含承诺 |

#### `hard` Commitment 的正式定义（CC-20260927-01 明确）

> `hard` Commitment 在**正常 Decision 流程中，不可被普通随机性、低优先级偏好覆盖**。
>
> 但 `hard` **不等于"永远不可违背"**。若世界硬约束导致无法履行（如医疗、封锁、物理不可达、更高强度的用户承诺），**必须允许可审计的失约 / 取消 / 重新规划**。

**因此 `hard` Commitment 的正确语义是：**

- 在 Decision 中拥有**最高非世界性优先级**；
- 不能被随机性 / 低优先级 Goal / 低优先级偏好覆盖；
- 但可以被**世界硬约束**或**更高强度的用户承诺**覆盖；
- 覆盖必须**可审计**（记录 reason 与覆盖者）。

#### 冻结规则

| 规则 | 内容 |
|------|------|
| **CO-1** | 本阶段**不实现** Commitment |
| **CO-2** | 不修改现有 `date_invites` / `date_invites_out` / `ai_meeting` 状态 |
| **CO-3** | 不修改现有 date / meeting 状态机 |
| **CO-4** | Commitment 状态转换**单向**，不允许 `FULFILLED → ACTIVE` |
| **CO-5** | Commitment 状态转换必须**可审计** |
| **CO-6** | Commitment 状态转换**不直接修改 `main.data`** |
| **CO-7** | 用户承诺**不得**被 AI↔AI 承诺覆盖 |
| **CO-8** | AI↔AI 承诺**不得**被随机性覆盖 |
| **CO-9** | AI 对自己的承诺**不得**被随机性覆盖 |
| **CO-10** | `hard` Commitment **不可**被普通随机性 / 低优先级偏好覆盖 |
| **CO-11** | `hard` Commitment **可以**被世界硬约束 / 更高强度用户承诺覆盖；覆盖必须可审计 |
| **CO-12** | Commitment 可以产生 Goal |
| **CO-13** | Commitment 可以约束 Motivation / Decision |
| **CO-14** | Goal **不能**反向修改 Commitment |
| **CO-15** | Commitment 可以关联 Activity，但 **Commitment ≠ Activity** |
| **CO-16** | Commitment 必须能够**跨 Event 持续存在** |
| **CO-17** | Commitment **最终持久化位置未冻结**（见 §5A.5） |

### 5A.4 Intent

#### 定义

> **Intent = 我现在倾向做什么。**

#### 性质（冻结）

| 规则 | 内容 |
|------|------|
| **IN-1** | Intent 是**结构化**对象 |
| **IN-2** | Intent 必须**可审计** |
| **IN-3** | Intent 必须携带 **Motivation / reason** |
| **IN-4** | Intent **不产生副作用** |
| **IN-5** | Intent **不直接修改 `main.data`** |
| **IN-6** | Intent **不直接触发 Action** |
| **IN-7** | Intent **不持久化** |
| **IN-8** | Intent **不跨 Event 存活** |
| **IN-9** | THINK **可以**产生多个候选 Intent |
| **IN-10** | Decision **负责**从候选 Intent 中选择最终 Intent |
| **IN-11** | THINK **不允许**选择最终 Intent |
| **IN-12** | Intent **不允许**直接执行 |
| **IN-13** | Intent 最终数据结构**未冻结**，留待后续 Contract Change |
| **IN-14** | `think(context) -> Optional[str]` 是 B5 临时占位，**不代表**最终 Intent Contract |
| **IN-15** | 本阶段**不实现** Intent |

#### Intent 到跨 Event 连续性的承担（CC-20260927-01 明确）

**关键规则：**

> Intent 不持久化是可以的，但必须明确：
>
> **Intent → Decision → Action 后，如果形成持续活动，由 Activity / Commitment / Goal 承担跨 Event 连续性。**
>
> **不能导致长活动断裂。**

因此未来必须满足：

1. Intent 是**单次 THINK 输出**，不跨 Event。
2. Decision 选择后，Intent 的生命周期结束。
3. 若 Decision 形成**持续活动**（如周末陪伴 / 医疗陪伴 / 旅行），该活动的跨 Event 连续性由：
   - **Activity Lifecycle**：承载"活动正在进行"；
   - **Commitment**：承载"承诺仍在生效"；
   - **Goal**：承载"目标尚未完成"。
4. **不允许**因为 Intent 不持久化，导致长活动在下一个 Event 到来时断裂。
5. **不允许**为了让长活动连续而让 Intent 持久化。

**因此未来正式链：**

```text
Event
  → THINK
  → Intent candidates
  → Decision
  → Action
  → Activity Lifecycle（承载跨 Event 连续性）
       ↑
  Goal / Commitment 持续生效
```

### 5A.5 Goal / Commitment 持久化与 Source of Truth（CC-20260927-01 核心）

#### 必须同时满足的三条

1. Goal / Commitment **必须能够跨 Event 持续存在**。
2. Goal / Commitment **不得写入 `main.data`**（SOT-1 / AS-5 仍生效）。
3. Goal / Commitment **不得产生第二套平行数据库**。

#### 与 `main.data` 唯一 Source of Truth 的关系（冻结）

| 规则 | 内容 |
|------|------|
| **SOT-7** | `main.data` 仍是 V3.1 唯一 Source of Truth |
| **SOT-8** | Goal / Commitment **不是** `main.data` 的子结构，**不是** 第二 Source of Truth |
| **SOT-9** | Goal / Commitment **不得**与 `main.data` 双向同步 |
| **SOT-10** | Goal / Commitment 可以在未来拥有自己的持久化机制，但该机制**不得**产生第二个与 `main.data` 平行、同等权威的事实源。持久化介质必须在权威性上从属于 `main.data`，或被设计为可从 `main.data` 重建的只读投影。**不允许出现两个独立、平等、相互同步的 Source of Truth。** |

### 5B.16 Runtime holder 边界（CC-20260928-03 新增）

**目的：**

明确 `AgentRuntime` 持有的 Goal / Commitment working state 的最小 API 边界。

**holder 结构（冻结）：**

```python
class AgentRuntime:
    def __init__(self, ...):
        ...
        self._goals: Dict[str, Goal] = {}
        self._commitments: Dict[str, Commitment] = {}
```

**最小 holder API（冻结）：**

| API | 语义 | 边界 |
|-----|------|------|
| `add_goal(goal) -> Goal` | 添加 Goal 到 holder | `goal_id` 已存在 → **reject**；禁止隐式 upsert |
| `get_goal(goal_id) -> Optional[Goal]` | 按 ID 查找 | 不存在 → 返回 `None` |
| `list_goals() -> List[Goal]` | 列出所有 Goal | 返回副本或只读视图（不允许外部修改内部 dict） |
| `replace_goal(goal) -> Goal` | 替换已存在的 Goal | `goal_id` 不存在 → **reject** |
| `add_commitment(commitment) -> Commitment` | 同 Goal | 同 Goal |
| `get_commitment(commitment_id) -> Optional[Commitment]` | 同 Goal | 同 Goal |
| `list_commitments() -> List[Commitment]` | 同 Goal | 同 Goal |
| `replace_commitment(commitment) -> Commitment` | 同 Goal | 同 Goal |

**冻结规则：**

| 规则 | 内容 |
|------|------|
| **RS-31** | Runtime holder 只负责"持有 + 读取 + 替换" |
| **RS-32** | Runtime holder **不负责状态机**；状态变化必须通过 `transition_goal()` / `transition_commitment()` 生成新对象 |
| **RS-33** | `add_goal()` / `add_commitment()` 在 ID 已存在时必须 **reject**；禁止隐式 upsert |
| **RS-34** | `replace_goal()` / `replace_commitment()` 在 ID 不存在时必须 **reject** |
| **RS-35** | `_goals` / `_commitments` 是 Runtime 内部状态，外部不得直接修改 |
| **RS-36** | 不允许提供"自动 transition" / "自动过期" / "冲突解决" / "优先级" API |
| **RS-37** | 不允许提供"自动 Goal / Commitment 创建" API |
| **RS-38** | 不允许提供"AI↔AI negotiation" API |
| **RS-39** | 不允许提供"持久化 / 数据库 / 文件" API |
| **RS-40** | 不允许提供"与 `main.data` 双向同步" API |

**与 `transition_*` 的协作模式（冻结）：**

```text
调用方：
    1. goal = create_goal(...)
    2. runtime.add_goal(goal)
    3. new_goal = transition_goal(goal, "ACTIVE", reason)
    4. runtime.replace_goal(new_goal)
```

**Runtime 不自动调用 `transition_*`。**

**五态核心正式定义（冻结，恰好 5 个）：**

| 状态 | 定义 | 语义含义（供未来 Agent Reasoning 使用） |
|------|------|----------------------------------------|
| **`FOUND`** | 当前能确定 | 直接使用 |
| **`ABSENT`** | **权威 World 数据明确表明不存在** | 它确实不存在 |
| **`UNKNOWN`** | **理论上可以回答，但当前事实不足** | 应继续询问 / 观察 / 搜索 |
| **`UNSUPPORTED`** | **当前 schema / Query 能力根本不能回答** | 当前世界系统没有这个能力 |
| **`AMBIGUOUS`** | **当前数据匹配到多个候选，无法唯一确定** | 需要消歧 |

> **架构侧强调：** 这一区分直接影响 AI 的「真人感」。
> `UNKNOWN` 与 `UNSUPPORTED` 若都返回 `None`，AI 将无法判断「没有医院」还是「系统不知道」还是「schema 答不了」。

### 5D.6.1 FORBIDDEN 与五态的关系（架构侧裁决，冻结）

> **裁决：`FORBIDDEN` 属 visibility / authorization outcome，**
> **不应与 `UNKNOWN` 等价。**

**语义关系（冻结）：**

```text
五态核心（status）  = 关于「世界 / schema 是否可回答」的认识论结论
                       FOUND / ABSENT / UNKNOWN / UNSUPPORTED / AMBIGUOUS

FORBIDDEN          = 关于「这个 requester 是否被允许知道」的授权结论
```

**两者正交：**

| 组合 | 含义 |
|------|------|
| `ALLOWED` + `FOUND` | 允许知道，且世界有该事实 |
| `ALLOWED` + `UNKNOWN` | 允许知道，但当前事实不足 |
| `ALLOWED` + `UNSUPPORTED` | 允许问，但 schema 答不了 |
| **`FORBIDDEN` + （status 不适用）** | **不允许知道 —— 此时不回答事实，也不推断「不存在」** |

**因此：**

```text
FORBIDDEN ≠ UNKNOWN
FORBIDDEN ≠ ABSENT
FORBIDDEN ∉ 五态核心
```

**为什么必须分开（产品与推理双重理由）：**

1. **产品理由：** `UNKNOWN` 会让 AI 认为「我可以继续观察 / 询问」，从而**反复试探**；
   而 `FORBIDDEN` 表示「**这条信息不在你的可见范围**」，AI 不应把它当作认知缺口去追求。
2. **推论理由：** 若把 `FORBIDDEN` 折叠为 `ABSENT`，AI 会**错误地认为事实不存在**；
   若折叠为 `UNKNOWN`，AI 会**错误地认为自己只是没观察到**。
   两者都会污染后续 Motivation / Intent / Decision。

| 规则 | 内容 |
|------|------|
| **WQ-113** | **五态核心恰好是 5 个**：`FOUND` / `ABSENT` / `UNKNOWN` / `UNSUPPORTED` / `AMBIGUOUS`；**`FORBIDDEN` 不属于五态核心** |
| **WQ-114** | `FORBIDDEN` 正式定义为 **visibility / authorization outcome**，与 `status` **正交**（建议以独立字段表达，如 `outcome`） |

### 5D.11 反模式：禁止把 Query 做成「万能世界 API」

> 这是 D-1 最容易犯的错误 —— 不是代码 bug，而是把 Query 做成万能 API。

**✅ 允许的形态：**

```text
World Query
   ├── Location（Building / Room / Facts）
   ├── People（AI / User / NPC —— 受可见性约束）
   └── Time（World Time / Room Time）
```

**❌ 禁止的形态：**

```text
WorldQuery
   ├─ find route
   ├─ decide where to go
   ├─ determine activity
   ├─ choose target
   ├─ search medical place
   ├─ calculate motivation
   ├─ create goal
   ├─ execute action
   └─ send SMS
```

| 规则 | 内容 |
|------|------|
| **WQ-90** | World Query **只回答「现在是什么」**；不得包含任何「应该去哪 / 选谁 / 做什么」语义 |
| **WQ-91** | **禁止**提供 route / planning / selection / ranking / recommendation 类接口 |
| **WQ-92** | 接口命名必须表达**事实询问**（`get_*` / `is_*` / `list_*`）；**禁止** `find_best_*` / `choose_*` / `decide_*` / `suggest_*` |
| **WQ-93** | 若某查询需要「为调用方挑一个最优解」，它**不是** World Query，必须在 D-1 Contract 中被拒绝 |

> **后者就是正在拆掉的 `ext_ai` / 万能分发器的另一种变体。**

### 5D.16.2 D-1 静态边界断言的实现策略（冻结）

> **来源：** D-0 / D-1 架构测试**首次真实运行**所暴露的 6 处缺陷（全部位于测试/文档层，无一在生产架构中）。
> 其中一处为**关键缺陷**：门状态判定把「标记当前不存在」这句**否定说明**误读为开门标记，导致 `GATE STATE: OPEN` 误报。

#### 核心教训

> **静态边界断言必须区分「代码构造」与「说明文本」。**

本项目的代码与文档中**大量存在否定式说明**，而这些说明**恰恰是在声明约束成立**。把它们当作违规会产生**系统性误报**。

**真实误报实例（三处，同一根因的不同变体）：**

| 类型 | 实例 | 被误判为 |
|------|------|---------|
| docstring | `agent/context.py`：`7. 不启用 ext_memory` | 引用 `ext_memory`（ME-22 违规） |
| docstring | `agent/event.py`：`3. 不接 EventBus / Scheduler / ...` | 建立 EventBus（EV-14 违规） |
| **方法体内多行字符串** | `agent/long_term_provider.py` 的 `describe()`：`"notes": ("…" "… ext_memory 未修复、未启用；" …)` | 引用 `ext_memory`（ME-22 违规） |
| **文档中的否定状态声明** | Contract：`D1G-3-SATISFIED` / `当前不存在` | 门已打开（`GATE STATE: OPEN`） |

#### 冻结规则

| 规则 | 内容 |
|------|------|
| **D1G-16** | **静态边界断言必须区分「代码构造」与「说明文本」**。说明文本（comment / docstring / 字符串字面量）**不得**被当作代码级耦合或违规的证据 |
| **D1G-17** | 检测符号出现时必须**按 token / AST 语义**判断，不得依赖**裸文本包含**；字符串字面量内容必须被掩掉（`x = "ext_memory"` 这类**代码级**耦合仍应检出，但其**字符串内容**不构成耦合） |
| **D1G-18** | **带开合语义的状态标记必须区分肯定式与否定式**。判定「标记已生效」时，只有**肯定式、独立成行**的标记才成立；含否定语境（「不存在」「未标记」「CLOSED」等）的行**必须**判为未生效 |
| **D1G-19** | **禁止用裸字符串包含判断否定式状态声明**（例如「标记 X 当前不存在」不得被读成「X 已生效」）。此类判定必须可审计，并明确写出判定规则 |
| **D1G-20** | **对否定式语义的断言应优先采用正向表述**：与其断言「不得出现 X」（易被说明文本误伤），不如断言「允许集合中只有 Y」，或先掩掉说明文本再断言 |

#### 已采纳的实现方式（供 D-1 / 后续阶段复用）

| 需求 | 采纳方式 |
|------|---------|
| 屏蔽说明文本 | `tokenize` 级处理：丢弃 `COMMENT`，将 `STRING` 掩为 `""`，其余原样保留（可正确处理**三引号 / 多行隐式拼接 / f-string**） |
| 检测「是否存在某实现」 | AST 级：只识别 `ClassDef` / `Call` 等**真实构造**，不扫描字符串 |
| 判定状态标记是否生效 | 逐行判定：**含肯定式标记** 且 **不含否定语境词**，才视为生效 |

#### 说明（重要：这不是架构原则）

| 规则 | 内容 |
|------|------|
| **D1G-21** | 本节属于 **D-1 静态验证策略的配套实现约定**，与 `D1G-11` ～ `D1G-15` 同属一层；**不是**对 Python 语言或未来架构的主张 |
| **D1G-22** | 若未来引入更精确的静态分析（类型系统 / 语义分析 / 专用 lint），本节策略**可以相应放宽**，但必须仍满足「静态可验证」且**不得退化为裸文本包含** |

#### 附带结论（必须记录）

>

### 5D.16.3 静态只读策略的唯一例外：深拷贝（D-1 Implementation Hardening）

> **来源：** D-1 Implementation Review（架构侧）。
> 审核指出 `get_building()` / `get_room()` 使用**浅复制**，
> nested dict / list 仍引用 `main.data` 内部对象 —— 违反 `WQ-78` / `WQ-79` / `WQ-103`。

#### 冻结规则

| 规则 | 内容 |
|------|------|
| **D1G-23** | **`copy.deepcopy` 是本 Contract 唯一允许的「表面违反就地修改禁令」的例外** |
| **D1G-24** | 该例外成立的依据：`deepcopy` **构造新对象**，**不就地修改输入**，因此不违反 `WQ-5` ～ `WQ-9`（READ ONLY），也不属于任何被禁写入模式 |
| **D1G-25** | 该例外的用途**仅限**：生成 `QueryResult.value` 的**安全副本**，以满足 `WQ-78` / `WQ-79` / `WQ-103`（任何嵌套结构都不得暴露 `main.data` 内部可变引用）。**不得**用于任何其他目的 |

#### 浅复制为什么不够（必须记录）

```text
building
 └── nested dict
      └── nested list      ← 浅复制后仍指向 main.data

result.value["nested"]["deep"]["layer"].append(x)
        ↓
main.data 被修改      ← 违反 WQ-79 / WQ-103
```

「只读」在 Python 中不是语言级保证（`WQ-101`）。
因此**返回值必须与 `main.data` 完全脱钩**，而不仅是顶层。

#### 与静态验证策略的关系

| 项 | 说明 |
|----|------|
| 是否放宽 `D1G-11` ～ `D1G-15` | **否**。就地修改类写法仍然全面禁止 |
| 是否新增允许项 | 仅 `copy.deepcopy` 一项 |
| 是否需要架构审核 | **是**，本例外经 D-1 Implementation Review 明确许可 |

## 5E. Phase D-2 Activity Contract（CC-20260930-06）

**版本：** `2026-09-30`
**依据：** `docs/D2_ACTIVITY_CONTRACT_PREFLIGHT.md`（**APPROVED WITH ARCHITECTURAL CORRECTIONS**）

### 5E.0 本节的地位与 D-2 的唯一目标

D-2 唯一要回答的问题是：

> **AI 正在做什么事情，而且这个事情为什么能够跨 Event 持续？**

即从 D-1 的：

```text
World Query = 世界事实（现在是什么）
```

进入：

```text
Activity    = 持续世界过程（正在经历什么）
```

| 规则 | 内容 |
|------|------|
| **EA-1** | D-2 **只建立** Activity 的正式语义、边界、生命周期与归属 |
| **EA-2** | D-2 **不实现** Activity 的任何运行时代码（`agent/activity.py` 在 D-2 **禁止创建**） |
| **EA-3** | D-2 **不实现** Activity Runtime / persistence / scheduler / Event 集成 / Movement 集成 / Capability 集成 |
| **EA-4** | D-2 **不迁移** `ext_world` / `ext_ai` / 任何 `ext_*` |
| **EA-5** | D-2 **不进入** D-3 |
| **EA-6** | 本节继承 §5C（D-0）与 §5D（D-1）的全部未撤销规则 |

---

### 5E.1 Activity 的严格定义

> **Activity = 世界之中一个具有身份、可持续、会结束的「过程」；
> 它描述「谁，正在经历什么」，而不是「谁想做什么」或「谁做了什么」。**

**四个必要条件（缺一不可）：**

| # | 条件 | 含义 | 反例 |
|---|------|------|------|
| 1 | **身份** identity | 同一过程跨 Event 保持同一，可被引用 | 每次 tick 新生成的派生标签 |
| 2 | **持续** duration | 生命周期跨越多个 Event | 单次 `speak` 是 Action |
| 3 | **参与者** participants | 至少一个 `actor` | 「城市在下雨」是 World Fact |
| 4 | **可终止** termination | 终态可达 | 「AI 活着」 |

| 规则 | 内容 |
|------|------|
| **EA-7** | Activity 必须同时满足上述**四个必要条件**；缺一即**不是** Activity |
| **EA-8** | Activity 的正式抽象地位见 `AC-5`：未来**唯一**正式的「持续世界过程」抽象 |
| **EA-9** | Activity **必须可解释**：能回答「为什么他现在在做这个」（经 `goal_id` / `commitment_ids` / `origin`），**不得**只给出无来源的标签 |
| **EA-10** | Activity **不得**用随机性解释其存在或变更（`INVARIANT-18`） |

### 5E.2 语义分层（Activity 与相邻概念的边界）

```text

Event        = 世界刚刚发生了什么        （agent.Event / EV-9）
Activity     = 谁正在经历什么持续过程    （D-2：本节）
Goal         = 我想完成什么              （C-2 / Runtime-only）
Commitment   = 我答应 / 承诺了什么        （C-2 / Runtime-only）
Intent       = 我当前倾向于做什么        （C-2 / Runtime-only）
Motivation   = 我为什么想做              （C-2 / 纯函数）
Decision     = 最终选择什么              （未实现 / Phase F）
Action       = 实际执行                  （Legacy：execute_action）
Scheduler    = 什么时候触发什么          （§14）
```

| 规则 | 内容 |
|------|------|
| **EB-1** | Activity ≠ World Fact；Activity 不得复制 World 事实（见 `EO-*`） |
| **EB-2** | Activity ≠ Event；Event 是已发生的通知，Activity 是持续的过程 |
| **EB-3** | Activity ≠ Goal（`AC-8` / `INVARIANT-5`） |
| **EB-4** | Activity ≠ Commitment（`AC-8` / `INVARIANT-6`） |
| **EB-5** | Activity ≠ Intent |
| **EB-6** | Activity ≠ Action |
| **EB-7** | Activity ≠ Motivation |
| **EB-8** | Activity ≠ Scheduler Entry |
| **EB-9** | Activity **可以引用** `goal_id` / `commitment_ids`，但**引用 ≠ 拥有**；Goal / Commitment 仍归 Runtime holder |
| **EB-10** | Activity **不得**被用作 Goal / Commitment / Intent / Motivation 的存储 |
| **EB-11** | Activity **不得**由 Intent 直接创建（`IN-6`：Intent 不直接触发副作用） |
| **EB-12** | Event **不得**直接修改 Activity（`EV-3` / `EV-4`）；Event 只被感知，由 Agent 链决定是否影响 Activity |
| **EB-13** | Activity **可以产生** Event（生命周期转换 → Event），但该 Event 的权威定义属 **D-1 / D-5 Event Coverage**；D-2 **不实现** Event 生产 |
| **EB-14** | Activity **不得**承担 Goal / Commitment / Intent 的持久化职责 |

### 5E.6 生命周期（Lifecycle）

**继承 D-0 Preflight §12 候选，本节正式冻结：**

```text
PLANNED ──→ TRAVELING ──→ ARRIVED ──→ ACTIVE ⇄ PAUSED ──→ COMPLETED
   │            │                       │        │
   └────────────┴───────────────────────┴────────┴──────→ CANCELLED
```

**允许转换（冻结）：**

| From | To |
|------|-----|
| `PLANNED` | `TRAVELING` / `CANCELLED` |
| `TRAVELING` | `ARRIVED` / `CANCELLED` |
| `ARRIVED` | `ACTIVE` / `CANCELLED` |
| `ACTIVE` | `PAUSED` / `COMPLETED` / `CANCELLED` |
| `PAUSED` | `ACTIVE` / `CANCELLED` |
| `COMPLETED` | （终态，无出边） |
| `CANCELLED` | （终态，无出边） |

| 规则 | 内容 |
|------|------|
| **EF-1** | 生命周期**固定**为：`PLANNED` / `TRAVELING` / `ARRIVED` / `ACTIVE` / `PAUSED` / `COMPLETED` / `CANCELLED` |
| **EF-2** | 只允许上表列出的转换；**禁止随意跳跃** |
| **EF-3** | `COMPLETED` / `CANCELLED` 是**终态**，**不可逆** |
| **EF-4** | 状态转换必须**单向且可审计** |
| **EF-5** | `CANCELLED` **必须携带原因**，不得静默取消 |
| **EF-6** | 生命周期**变更必须产生 Event**（`EB-13`）；但 **D-2 不实现** Event 生产 |
| **EF-7** | Activity 的**状态只能**通过显式转换 API 修改；**禁止**外部直接改内部字段 |
| **EF-8** | D-2 **只定义**状态机语义，**不实现**转移执行 |
| **EF-9** | **禁止**状态转换由随机性决定 |
| **EF-10** | 「谁在何时推动状态转换」**不在 D-2 冻结**（依赖未冻结的 Decision / Capability） |

**禁止的跳跃（冻结，逐条列举）：**

> `EF-2` 不止是一句「禁止随意跳跃」——以下具体跳跃**必须被编译器 / 实现拒绝**。

```text
❌ PLANNED → COMPLETED（跳跃，无业务原因）
❌ PLANNED → ACTIVE（跳过 TRAVELING / ARRIVED）
❌ PLANNED → ARRIVED（跳过 TRAVELING）
❌ PLANNED → PAUSED（尚未开始，无法暂停）
❌ TRAVELING → COMPLETED（跳过 ARRIVED / ACTIVE）
❌ TRAVELING → ACTIVE（跳过 ARRIVED）
❌ ARRIVED → COMPLETED（跳过 ACTIVE）
❌ ARRIVED → PAUSED（尚未 ACTIVE，无法暂停）
❌ PAUSED → COMPLETED（必须先经 ACTIVE）
❌ COMPLETED → ACTIVE（终态不可逆）
❌ COMPLETED → CANCELLED（终态不可逆）
❌ CANCELLED → ACTIVE（终态不可逆）
❌ CANCELLED → COMPLETED（终态不可逆）
```

| 规则 | 内容 |
|------|------|
| **EF-11** | 上列跳跃**必须**被拒绝；实现**不得**提供绕过路径 |
| **EF-12** | 「先跳到 `COMPLETED` 再补 `ACTIVE`」这类**补写**同样禁止（终态不可逆） |
| **EF-13** | 若未来确需新增允许转换，**必须**经独立 Contract Change 修改 §5E.6 的允许转换表 |

### 5E.7 Actor / Participant / Role

**架构侧裁决（第 5 节关闭）：**

```text
actor_ids       = 对该 Activity 承担「正在进行」主体的实体
participant_ids = 参与该 Activity 的其他实体
role_map        = 参与者角色
```

**示例（DATE）：**

```text
actor       : AI
participant : User
```

| 规则 | 内容 |
|------|------|
| **EG-1** | Activity 用**统一的** `actor_ids` + `participant_ids` 表达参与者 |
| **EG-2** | `actor_ids` = 承担「正在进行」主体的实体；**必须至少包含一个主体**（`EA-7` 条件 3） |
| **EG-3** | `participant_ids` = 参与该 Activity 的其他实体 |
| **EG-4** | `role_map` 表达参与者角色 |
| **EG-5** | **禁止**为 AI↔AI / AI↔User / AI↔NPC 各造一套参与者结构 |
| **EG-6** | AI↔AI 活动与 AI↔User 活动**使用同一结构**，仅 `role` 与参与者类型不同 |
| **EG-7** | **NPC 在 D-2 不作为 Autonomous Activity Owner** |
| **EG-8** | NPC **可以作为** Activity 的 `participant` / `role` |
| **EG-9** | **纯 NPC 之间的活动**在 D-2 **不建模**（当前 schema 中 NPC 没有位置 / 状态）→ `UNSUPPORTED` |
| **EG-10** | `role` 的完整取值集合**不在 D-2 冻结**；但**至少**必须能表达「主体」与「参与」的区分 |
| **EG-11** | 参与者引用**不得**复制实体事实（位置 / 状态），只能引用（见 `EO-*`） |

### 5E.8 Persistence 与 Restart 语义

| 规则 | 内容 |
|------|------|
| **EH-1** | **D-2 的 Activity 不持久化**（不写文件 / DB / `main.data`） |
| **EH-2** | D-2 **不引入** Activity 的持久化机制 |
| **EH-3** | D-2 明确：Activity **跨重启丢失** |
| **EH-4** | 重启后 Legacy 活动状态（18 类）**仍然存在**（它们本就在 `main.data`） |
| **EH-5** | 因此重启后 Activity **必须能从 Legacy 状态重建** |
| **EH-6** | 重建是**只读投影**，**禁止**反向写入 Legacy 字段 |
| **EH-7** | 重建后的 Activity **identity 不保证与重启前一致**（D-2 已知限制，必须记录） |
| **EH-8** | D-2 **不得**为了让 identity 跨重启稳定而引入持久化 |
| **EH-9** | D-2 的连续性保证**仅限**「跨 Event（同一运行期内）」 |

**必须诚实记录的限制：**

```text
D-2 的 Activity 连续性保证是「跨 Event」，不是「跨重启」。
跨重启的 Activity 连续性 = 需要 persistence 裁决 = 后续 Contract Change。
```

### 5E.9 生命周期与 Event 打断

| 规则 | 内容 |
|------|------|
| **EI-1** | Event **不得**直接修改 Activity 状态（`EB-12`）；打断必须经 Agent 链判断 |
| **EI-2** | 打断处理**必须**区分 **`PAUSED`（可恢复）** 与 **`CANCELLED`（终止）** |
| **EI-3** | **禁止**把一切打断一律处理为 `CANCELLED` |
| **EI-4** | `CANCELLED` **必须携带原因**（`EF-5`） |
| **EI-5** | 打断后的恢复**不得**创建新 identity（`PAUSED → ACTIVE` 是**恢复**，不是新 Activity） |
| **EI-6** | Activity 的打断与恢复**不得**由随机性决定 |
| **EI-7** | 「谁有权打断 Activity」**不在 D-2 冻结** |
| **EI-8** | World 硬约束导致不可继续时，属 `CANCELLED`（附原因），**不是** `PAUSED` |

**四种打断语义（必须区分）：**

| 语义 | 处理 |
|------|------|
| 中断可恢复 | `ACTIVE → PAUSED → ACTIVE` |
| 被更高优先级过程取代 | `ACTIVE → CANCELLED` + 新 Activity |
| 自然结束 | `ACTIVE → COMPLETED` |
| World 硬约束不可继续 | `ACTIVE → CANCELLED` |

### 5E.11 并发性（Cardinality）

| 规则 | 内容 |
|------|------|
| **EK-1** | 一个 AI 在任意时刻**最多只有一个 `primary` Activity** |
| **EK-2** | 一个 AI **可以同时存在多个 `secondary` Activity** |
| **EK-3** | **禁止**同一 AI 存在两个 `primary` Activity |
| **EK-4** | `primary` 是**绑定关系**（`EE-8`），不是所有权 |
| **EK-5** | D-2 **不实现** primary 选举 / 抢占 / 优先级算法（需 Decision，属 Phase F） |
| **EK-6** | 一个 World 位置 / 房间内**可以同时存在多个** Activity |
| **EK-7** | 一个 Entity **可以同时是多个** Activity 的参与者（例如同时在「工作」与「挂机等待回复」中） |

**理由：** 真实角色人生中「一边工作一边等消息」是自然的；但「同时进行两个约会」不是。因此需要 `primary` / `secondary` 区分，而不是「只能有一个」。

### 5E.12 Activity 与 Goal / Commitment 的依赖强度

| 规则 | 内容 |
|------|------|
| **EL-1** | Activity **允许** `goal_id` 为空 |
| **EL-2** | `goal_id` 为空的 Activity **不得**被视为非法 |
| **EL-3** | 对 Goal 的引用是**弱引用**（Goal 消失不导致 Activity 非法） |
| **EL-4** | Activity **不要求**对应 Commitment；`commitment_ids` 可以为空 |
| **EL-5** | 由 Commitment 派生的 Activity **必须**引用该 Commitment（保证可审计） |
| **EL-6** | Commitment 被取消 / 过期时，其关联 Activity **不自动终止** |
| **EL-7** | Activity **不得**被用来替代 Commitment（`EB-4`） |

**理由：** 角色的日常过程（吃饭、散步、发呆）**不需要 Goal**；强制要求会把 Goal 变成 Activity 的存储。

### 5E.15 防「第二套 World SOT」

**六条防线：**

| 规则 | 内容 |
|------|------|
| **EO-1** | Activity **不得**复制 World 事实（位置、房间、建筑、NPC、钱包、好感…）为自有字段；只能**引用** |
| **EO-2** | Activity **不得**创建独立的持久化介质（`ED-7`） |
| **EO-3** | Activity **不得**成为任何 World Fact 的权威来源；冲突时以 World Query / `main.data` 为准 |
| **EO-4** | Activity **不得**与 Legacy Activity State 双向同步；只允许**单向只读派生** |
| **EO-5** | Activity **不得**被任何其他模块当作「事实来源」来读取 World 状态 |
| **EO-6** | 一旦发现「Activity 与 World Query 对同一事实给出不同答案」，**必须**视为架构缺陷并上报 |
| **EO-7** | Activity Registry **不得**成为 World 事实的第二来源（`ED-3` / `ED-4`） |

**单向只读派生的精确定义（D-2 关键约束）：**

```text
Legacy Activity State（18 类，main.data）
        ↓  只读派生（one-way，允许）
D-2 Activity（Runtime-scoped Domain State）

        ✗ Activity → Legacy 反向写入     禁止
        ✗ Activity ↔ Legacy 双向同步     禁止
```

| 规则 | 内容 |
|------|------|
| **EO-8** | D-2 阶段，Legacy → Activity 是**单向只读观察 / 重建**关系 |
| **EO-9** | **禁止** `Activity → Legacy` |
| **EO-10** | **禁止** `Activity ↔ Legacy` |
| **EO-11** | **禁止**双向同步 |
| **EO-12** | Legacy 字段**不能**被 Activity 修改、删除或反向写回 |
| **EO-13** | `D-6` 才处理 Legacy 字段的**归属迁移**；**D-2 不迁移** |
| **EO-14** | `AC-2` / `AC-3` / `AC-10` 在 D-2 继续生效 |

### 5E.16 防「变成 Scheduler」

| | Scheduler | Activity |
|---|---|---|
| 回答 | **什么时候**触发什么 | **谁正在经历什么** |
| 时间语义 | 触发时刻（future trigger） | 持续区间（duration） |
| 存在性 | 到点即消失 / 重排 | 有生命周期与身份 |
| 驱动 | 时间推进 | World Change / Decision |

| 规则 | 内容 |
|------|------|
| **EP-1** | Activity **不是** Scheduler |
| **EP-2** | Activity **不得**定义「到点触发」语义 |
| **EP-3** | Activity **不得**持有调度字段（`next_ts` / `next_shop_ts` 等） |
| **EP-4** | Activity **可以**有 `expected_end_at`（**预期**结束时间）—— 这是**描述**，不是**触发** |
| **EP-5** | **`expected_end_at` 到期不等于 Activity 自动结束** |
| **EP-6** | D-2 **禁止**实现任何 tick / loop / timer 驱动的 Activity 推进 |
| **EP-7** | Activity 的推进只能来自 **World Change → 感知 → Decision**（后续阶段），**不得**来自时间轮询 |
| **EP-8** | 现有 10 项节律 / 调度键（`story_rhythm` / `writing_rhythm` / `living_rhythm` / `ai_home_act_next` / `ai_auto_next` / `_last_think_invite` / `ai_drive_log` / `ai_last_human` / `ai_last_auto` / `ai_diary_log`）在 D-2 **仍属 Legacy 调度状态**，**不得**被改造成 Activity 字段 |
| **EP-9** | Activity Registry **不得**承担调度职责（`EE-12`） |
| **EP-10** | Activity 的存在**不得**产生任何后台轮询 |

> **`EP-5` 是本节最关键的一条：** 一旦「到期即结束」被允许，Activity 就退化为 Scheduler 的包装。

### 5E.22 D-2 阶段门（Pre / Post Implementation Gate）

> **来源：** D-2 Architecture Tests Review（架构侧）。
> 审核指出：**不得把「`agent/activity.py` 是否存在」当作 Gate OPEN/CLOSED 的判据** ——
> 那会把「实现存在」（implementation presence）与「架构授权实现」（implementation authorized）混为一谈。

**两个概念必须分开（冻结）：**

```text
implementation presence  = agent/activity.py（或 agent/activity/ 包）是否存在
                           —— 客观事实，任何一方都无法靠它取得授权

implementation authorized = 架构侧在门状态块中把 marker 置为 true
                           —— 唯一合法的开门依据
```

| 规则 | 内容 |
|------|------|
| **EG-12** | **禁止**把「文件存在」本身作为授权条件；文件存在只能说明 implementation presence |
| **EG-13** | 只有门状态块的 marker 为 `true` 才代表架构侧授权进入 **Post-Implementation Gate** |
| **EG-14** | Gate 的判定必须由 **Contract 显式标记**决定，**不得**由 DS 自行判断 |

**两个阶段门（与 D-1 §5D.16 同构）：**

| 门 | 名称 | 生效时机 | 断言内容 |
|----|------|---------|---------|
| **T-A** | **Pre-Implementation Gate** | Gate **CLOSED** 时 | Activity 实现**必须不存在**；不得提前创建 Activity / Registry / persistence / scheduler；不得提前做 Event / Capability / Motivation 集成 |
| **T-A** | 同一组，Gate **OPEN** 后 | Gate **OPEN** 时 | Activity 实现**必须存在**（否则无法形成正式通过状态） |
| **T-B** | **Post-Implementation Boundary Gate** | **仅实现存在时** | 继续执行**实现级**边界验证（persistence / scheduler / Event / Capability / Motivation / Legacy 写入 …） |

**关键的「不得跳过」规则（架构侧特别指出）：**

| 规则 | 内容 |
|------|------|
| **EG-15** | **严禁**「因为 `agent/activity.py` 已存在就 `return`」从而**跳过** persistence / scheduler / Event 等边界检查 |
| **EG-16** | 实现存在时，边界检查的**扫描目标**必须包含 **Activity 实现文件本身**，并覆盖全部边界项 |
| **EG-17** | 只有「该边界项在**当前阶段根本不适用**」时才允许不适用；**不得**因为实现存在而整体跳过 |

**禁止清单的有效性：**

| 规则 | 内容 |
|------|------|
| **EU-1** | 上列禁止项在 D-2 Contract 经架构审核通过**之后**仍然有效 |
| **EU-2** | 解除任何一项**必须**经独立 Contract Change |
| **EU-3** | D-2 的**下一个允许动作**只有：提交 Contract diff / SHA，等待架构审核 |

**Gate 状态（当前）—— 结构化、可机读、单一来源：**

```text
D2G-GATE-STATUS: CLOSED
D2G-3-MARKER: null
```

> **`D2G-GATE-STATUS` 是门状态的单一来源。**
> **`D2G-3-MARKER` 是授权标记：只有把它写成 `true` 才表示架构侧授权。**
>
> **开启门（仅架构侧可执行）**：把上面两行改为
> `STATUS = OPEN` 且 `MARKER = true`（以真实键值形式写入，不在此处复写）。
>
> **关闭门（默认）：** `MARKER = null`（或删除该行）。
>
> **重要（`D1G-16` 教训）：** 本小节是**唯一**允许出现该标记赋值的位置。
> **其它说明性文本不得使用标记的字面赋值形式** —— 否则会被静态判定读成「已开门」。
> **DS 不得自行写入该标记**，也不得因发现文件已存在而自行判为 OPEN。

## 21. 为什么 Context Foundation 是第一步

### Phase B（V3.1 Context Foundation）的必要性

**1. Context 是当前最痛的瓶颈**
- 每次对话 7k-10k tokens
- 上下文包含 15+ 片段
- 无分层、无预算、无按需检索

**2. Context 是后续所有阶段的前置依赖**
- Memory Recall → 需要 Context 分层
- Goal / Motivation → 需要 Context 提供状态
- Activity Lifecycle → 需要 Context 提供当前活动
- World Query → 需要 Context 提供世界状态

**3. Context Foundation 完全独立于业务代码**
- 只新增 `agent/context.py` 之类的模块
- 不修改 `build_ai_context`
- 可并行运行、独立测试

**4. 不做 Context Foundation 就进入 Goal/Motivation 会失控**
- 会导致 Goal 层自己去拼 context
- 会导致 Motivation 层重复读取 `main.data`
- 会破坏 Contract 的"单一 Source of Truth"原则

**结论**：Context Foundation 是**低风险、高价值、被所有后续阶段依赖**的第一步。
