## 0. 总原则

V3.1 = orchestration / control layer over existing Linkong capabilities

≠ 重写 Linkong
≠ 建立第二套 World
≠ 建立第二套 Source of Truth

**改造策略**：
- 先统一语义，再拆文件
- 先接管决策，再迁移执行
- 先并行观察，再逐步切换
- 旧功能不能坏

## 1. Source of Truth

### 冻结规则

| 规则 | 内容 |
|------|------|
| **SOT-1** | `main.data` 是当前唯一 Source of Truth |
| **SOT-2** | AgentState 是 Projection，**不是** Source of Truth |
| **SOT-3** | Event 是"事实描述"，**不是** Source of Truth |
| **SOT-4** | 不允许任何 V3.1 模块创建第二数据源 |
| **SOT-5** | 不允许任何 V3.1 模块双向同步 `main.data` |
| **SOT-6** | 任何"缓存"必须是只读投影或可重建 |
| **SOT-7** | **【CC-20260927-01】** `main.data` 始终是 V3.1 唯一 Source of Truth |
| **SOT-8** | **【CC-20260927-01】** Goal / Commitment 不是 `main.data` 的子结构，也不是第二 Source of Truth |
| **SOT-9** | **【CC-20260927-01】** Goal / Commitment 不得与 `main.data` 双向同步 |
| **SOT-10** | **【CC-20260927-01】** Goal / Commitment 可以在未来拥有自己的持久化机制，但该机制**不得**产生第二个与 `main.data` 平行、同等权威的事实源。持久化介质必须在权威性上从属于 `main.data`，或被设计为可从 `main.data` 重建的只读投影。**不允许出现两个独立、平等、相互同步的 Source of Truth。** |
| **SOT-11** | **【CC-20260927-01】** 具体实现方案（独立 JSON / SQLite / 内存 + 快照 / 其他）未冻结；最终权威性、重建关系、一致性边界未冻结；留待后续 Contract Change |

## 4. AgentRuntime

### 定义
单个 AI 的 orchestration 生命周期。

### 生命周期
```text
RECEIVE → PERCEIVE → WAKE_DECISION → CONTEXT
→ THINK → DECISION → ACTION → WORLD_CHANGE → EVENT
```

### 冻结规则

| 规则 | 内容 |
|------|------|
| **AR-1** | 一个 AI 一个 Runtime 实例（不是"超级 Runtime 管理所有 AI"） |
| **AR-2** | Runtime 不直接访问 `main.data`（只通过 Contract 方法） |
| **AR-3** | Runtime 不直接修改 World（只通过 Decision → Action 让现有 `ext_*` 修改） |
| **AR-4** | Runtime 不替代 `ext_ai`（**旁路观察**） |
| **AR-5** | P0-3B 感知链保持不变 |
| **AR-6** | P0-3B **不返回 THINK**（留给未来 Wake Score） |
| **AR-7** | Runtime 不成为 `main.data` 第二个数据库 |
| **AR-8** | **【CC-20260926-01】** Runtime 的 CONTEXT 阶段输出类型冻结为 `AgentContext`（见 §5），不再返回 `ContextLayers` |
| **AR-9** | **【CC-20260926-01】** Runtime 的 THINK 阶段输入类型冻结为 `AgentContext`，不再接收 `ContextLayers` |
| **AR-10** | **【CC-20260926-01】** Runtime 不得同时调用旧 `ext_ai.build_ai_context` 与新 `ContextAssembler` |

### Context 阶段正式接口（CC-20260926-01 冻结）

```python
def build_context(
    self,
    event: Event,
    now_ts: Optional[float] = None,
) -> AgentContext:
    ...

def think(self, context: AgentContext) -> Optional[str]:
    ...
```

> 注：`think() -> Optional[str]` 是 B5 阶段的临时占位 / 兼容接口，
> **不代表最终 Intent Contract**。最终 Intent 数据结构见 §5A.4，
> 具体 schema 留待后续 Contract Change 冻结。

### 数据来源冻结（CC-20260926-01）

| 参数 | 提供者 | 方式 |
|------|--------|------|
| `ai_name` | Runtime | `self.ai_name` |
| `owner` | Runtime | `get_state().owner` |
| `data` | Runtime | `self._data`（不透明引用） |
| `now_ts` | 调用方注入 | 缺省由 `ContextAssembler` 使用当前时间 |
| `agent_state_dict` | Runtime | `get_state().to_dict()` |
| `recall_query` | Runtime | 固定 `None`（本阶段） |

## 5. Context Assembly

### 定义
独立于旧 `build_ai_context` 的 Context 构造层。

### 正式 Context 标准（CC-20260926-01）

**V3.1 唯一正式 Context 数据结构 = `AgentContext`（`agent/context.py`）。**

```text
Event
  ↓
RECEIVE
  ↓
PERCEIVE
  ↓
WAKE_DECISION
  ↓
CONTEXT
  ↓
AgentRuntime.build_context()
  ↓
ContextAssembler
  ↓
AgentContext
  ↓
THINK（仍为 Stub）
```

该数据链为 V3.1 唯一正式 Context 数据链。

### 分层
| 层 | 内容 | 是否增长 |
|----|------|---------|
| **A. Stable Core** | 世界观 / 人设 / 核心用户信息 / 长期身份 | ❌ 稳定 |
| **B. Recent** | 当前对话 / 最近 Event / 当前活动 | ❌ 有界 |
| **C. Long-term** | Memory / Relationship / 历史事件 | ✅ 按需检索 |
| **D. Dynamic World** | AgentState / 当前地点 / 当前世界状态 | ❌ 瞬时 |

### 冻结规则

| 规则 | 内容 |
|------|------|
| **CA-1** | Context Assembly 与旧 `build_ai_context` **并行运行** |
| **CA-2** | 不修改旧 `build_ai_context` |
| **CA-3** | 目标：历史增长**不**导致单次 Context 线性增长 |
| **CA-4** | 不粗暴砍掉现有 7k-10k tokens（保护世界观 / 人设 / 关系 / Memory 连续性） |
| **CA-5** | Long-term 层必须**按需检索**，不默认全量注入 |
| **CA-6** | **【CC-20260926-01】** `AgentContext` 是 V3.1 唯一正式 Context 数据结构，禁止新建平行 Context 结构 |
| **CA-7** | **【CC-20260926-01】** `ContextLayers`（P0-3A）正式 **deprecated**，保留兼容 stub，不删除、不改名、不别名化；新 V3.1 链不再引用它 |
| **CA-8** | **【CC-20260926-01】** 不允许长期存在"双 Context"：旧 `build_ai_context` 与新 `ContextAssembler` 不得在同一 AI 决策周期内同时触发 |
| **CA-9** | **【CC-20260926-01】** `ContextAssembler` 只能被 `AgentRuntime.build_context()` 调用；其他调用方需 Contract 变更 |
| **CA-10** | **【CC-20260926-01】** `decision_constraints` 当前保持 `None`，不得提前实现 Goal / Motivation / Commitment |

### ContextLayers 兼容状态（CC-20260926-01）

- `ContextLayers` 定义保留在 `agent/runtime.py`。
- 语义：**deprecated compatibility stub**。
- 不允许：
  - 删除；
  - 改名；
  - 别名化（如 `ContextLayers = AgentContext`）；
  - 新 V3.1 链引用。

### 5A.1 Goal

#### 定义

> **Goal = 我想完成什么。**

#### 生命周期（冻结）

```text
CREATED → ACTIVE → COMPLETED
              │
              ├──→ CANCELLED
              │
              └──→ EXPIRED
```

| 状态 | 含义 | 是否终态 |
|------|------|---------|
| `CREATED` | 刚被创建，未激活 | 否 |
| `ACTIVE` | 正在追求 | 否 |
| `COMPLETED` | 已达成 | 是 |
| `CANCELLED` | 主动取消 | 是 |
| `EXPIRED` | 被动过期 | 是 |

#### 冻结规则

| 规则 | 内容 |
|------|------|
| **GO-1** | 本阶段**不实现** Goal |
| **GO-2** | Goal 状态转换**单向**，不允许 `COMPLETED → ACTIVE` |
| **GO-3** | Goal 状态转换必须**可审计**（记录 reason） |
| **GO-4** | Goal 状态转换**不直接修改 `main.data`** |
| **GO-5** | Goal 允许多个同时存在 |
| **GO-6** | Goal 来源仅限：用户要求 / Commitment / Relationship / Memory / 未完成 Activity / 工作日程世界约束 / AI 自身长期偏好 |
| **GO-7** | Goal **禁止**凭空生成 |
| **GO-8** | Goal **禁止**随机生成 |
| **GO-9** | Goal **禁止**由未经验证的 LLM 输出直接生成 |
| **GO-10** | AI 必须未来能够拥有**不来自用户要求**的生活目标 |
| **GO-11** | Goal 必须能够**跨 Event 持续存在**；单个 Event 不得让 Goal 无故消失 |
| **GO-12** | Goal 优先级算法、冲突解决规则**未冻结**，留待后续 Contract Change |
| **GO-13** | Goal **最终持久化位置未冻结**（见 §5A.5） |

### 5A.2 Commitment

#### 定义

> **Commitment = 我已经答应 / 约定 / 承诺什么。**

#### 生命周期（冻结）

```text
CREATED → ACTIVE → FULFILLED
              │
              ├──→ CANCELLED
              │
              └──→ EXPIRED
```

| 状态 | 含义 | 是否终态 |
|------|------|---------|
| `CREATED` | 刚形成 | 否 |
| `ACTIVE` | 有效 | 否 |
| `FULFILLED` | 已兑现 | 是 |
| `CANCELLED` | 已取消 | 是 |
| `EXPIRED` | 已过期 | 是 |

#### 四类承诺（冻结）

| 类型 | actor | counterparty | 默认强度 |
|------|-------|--------------|---------|
| AI → 用户 | AI | 用户 | `hard` |
| 用户 → AI | 用户 | AI | `hard` |
| AI → AI | AI A | AI B | `soft` |
| AI 对自己 | AI | 自己 | `soft` |

#### 强度分级（冻结）

| 强度 | 含义 |
|------|------|
| `hard` | 明确承诺 |
| `soft` | 模糊承诺 |
| `implicit` | 隐含承诺 |

#### `hard` Commitment 的正式定义（CC-20260927-01 明确）

> `hard` Commitment 在**正常 Decision 流程中，不可被普通随机性、低优先级偏好覆盖**。
>
> 但 `hard` **不等于"永远不可违背"**。若世界硬约束导致无法履行（如医疗、封锁、物理不可达、更高强度的用户承诺），**必须允许可审计的失约 / 取消 / 重新规划**。

**因此 `hard` Commitment 的正确语义是：**

- 在 Decision 中拥有**最高非世界性优先级**；
- 不能被随机性 / 低优先级 Goal / 低优先级偏好覆盖；
- 但可以被**世界硬约束**或**更高强度的用户承诺**覆盖；
- 覆盖必须**可审计**（记录 reason 与覆盖者）。

#### 冻结规则

| 规则 | 内容 |
|------|------|
| **CO-1** | 本阶段**不实现** Commitment |
| **CO-2** | 不修改现有 `date_invites` / `date_invites_out` / `ai_meeting` 状态 |
| **CO-3** | 不修改现有 date / meeting 状态机 |
| **CO-4** | Commitment 状态转换**单向**，不允许 `FULFILLED → ACTIVE` |
| **CO-5** | Commitment 状态转换必须**可审计** |
| **CO-6** | Commitment 状态转换**不直接修改 `main.data`** |
| **CO-7** | 用户承诺**不得**被 AI↔AI 承诺覆盖 |
| **CO-8** | AI↔AI 承诺**不得**被随机性覆盖 |
| **CO-9** | AI 对自己的承诺**不得**被随机性覆盖 |
| **CO-10** | `hard` Commitment **不可**被普通随机性 / 低优先级偏好覆盖 |
| **CO-11** | `hard` Commitment **可以**被世界硬约束 / 更高强度用户承诺覆盖；覆盖必须可审计 |
| **CO-12** | Commitment 可以产生 Goal |
| **CO-13** | Commitment 可以约束 Motivation / Decision |
| **CO-14** | Goal **不能**反向修改 Commitment |
| **CO-15** | Commitment 可以关联 Activity，但 **Commitment ≠ Activity** |
| **CO-16** | Commitment 必须能够**跨 Event 持续存在** |
| **CO-17** | Commitment **最终持久化位置未冻结**（见 §5A.5） |

### 5A.4 Intent

#### 定义

> **Intent = 我现在倾向做什么。**

#### 性质（冻结）

| 规则 | 内容 |
|------|------|
| **IN-1** | Intent 是**结构化**对象 |
| **IN-2** | Intent 必须**可审计** |
| **IN-3** | Intent 必须携带 **Motivation / reason** |
| **IN-4** | Intent **不产生副作用** |
| **IN-5** | Intent **不直接修改 `main.data`** |
| **IN-6** | Intent **不直接触发 Action** |
| **IN-7** | Intent **不持久化** |
| **IN-8** | Intent **不跨 Event 存活** |
| **IN-9** | THINK **可以**产生多个候选 Intent |
| **IN-10** | Decision **负责**从候选 Intent 中选择最终 Intent |
| **IN-11** | THINK **不允许**选择最终 Intent |
| **IN-12** | Intent **不允许**直接执行 |
| **IN-13** | Intent 最终数据结构**未冻结**，留待后续 Contract Change |
| **IN-14** | `think(context) -> Optional[str]` 是 B5 临时占位，**不代表**最终 Intent Contract |
| **IN-15** | 本阶段**不实现** Intent |

#### Intent 到跨 Event 连续性的承担（CC-20260927-01 明确）

**关键规则：**

> Intent 不持久化是可以的，但必须明确：
>
> **Intent → Decision → Action 后，如果形成持续活动，由 Activity / Commitment / Goal 承担跨 Event 连续性。**
>
> **不能导致长活动断裂。**

因此未来必须满足：

1. Intent 是**单次 THINK 输出**，不跨 Event。
2. Decision 选择后，Intent 的生命周期结束。
3. 若 Decision 形成**持续活动**（如周末陪伴 / 医疗陪伴 / 旅行），该活动的跨 Event 连续性由：
   - **Activity Lifecycle**：承载"活动正在进行"；
   - **Commitment**：承载"承诺仍在生效"；
   - **Goal**：承载"目标尚未完成"。
4. **不允许**因为 Intent 不持久化，导致长活动在下一个 Event 到来时断裂。
5. **不允许**为了让长活动连续而让 Intent 持久化。

**因此未来正式链：**

```text
Event
  → THINK
  → Intent candidates
  → Decision
  → Action
  → Activity Lifecycle（承载跨 Event 连续性）
       ↑
  Goal / Commitment 持续生效
```

### 5A.5 Goal / Commitment 持久化与 Source of Truth（CC-20260927-01 核心）

#### 必须同时满足的三条

1. Goal / Commitment **必须能够跨 Event 持续存在**。
2. Goal / Commitment **不得写入 `main.data`**（SOT-1 / AS-5 仍生效）。
3. Goal / Commitment **不得产生第二套平行数据库**。

#### 与 `main.data` 唯一 Source of Truth 的关系（冻结）

| 规则 | 内容 |
|------|------|
| **SOT-7** | `main.data` 仍是 V3.1 唯一 Source of Truth |
| **SOT-8** | Goal / Commitment **不是** `main.data` 的子结构，**不是** 第二 Source of Truth |
| **SOT-9** | Goal / Commitment **不得**与 `main.data` 双向同步 |
| **SOT-10** | Goal / Commitment 可以在未来拥有自己的持久化机制，但该机制**不得**产生第二个与 `main.data` 平行、同等权威的事实源。持久化介质必须在权威性上从属于 `main.data`，或被设计为可从 `main.data` 重建的只读投影。**不允许出现两个独立、平等、相互同步的 Source of Truth。** |
| **SOT-11** | 具体实现方案（独立 JSON / SQLite / 内存 + 快照 / 其他）**未冻结**；最终权威性、重建关系、一致性边界**未冻结**；留待后续 Contract Change |

#### 与现有日期 / 会议状态的关系

- `date_invites` / `date_invites_out` / `ai_meeting` / `work_sessions` / `dates` / `ai_shop_state` / `instances` **保持不变**。
- 未来 Commitment 可以从这些字段**读取**，但**不反向写入**。
- 未来 Commitment 形成后，**不修改**这些字段。

#### 未冻结项（必须留待后续 Contract Change）

- Goal 最终持久化位置。
- Commitment 最终持久化位置。
- 是否复用 `main.data`。
- 是否独立 JSON / SQLite / 内存 + 快照。
- Goal / Commitment 是否需要独立数据库。

## 21. 为什么 Context Foundation 是第一步

### Phase B（V3.1 Context Foundation）的必要性

**1. Context 是当前最痛的瓶颈**
- 每次对话 7k-10k tokens
- 上下文包含 15+ 片段
- 无分层、无预算、无按需检索

**2. Context 是后续所有阶段的前置依赖**
- Memory Recall → 需要 Context 分层
- Goal / Motivation → 需要 Context 提供状态
- Activity Lifecycle → 需要 Context 提供当前活动
- World Query → 需要 Context 提供世界状态

**3. Context Foundation 完全独立于业务代码**
- 只新增 `agent/context.py` 之类的模块
- 不修改 `build_ai_context`
- 可并行运行、独立测试

**4. 不做 Context Foundation 就进入 Goal/Motivation 会失控**
- 会导致 Goal 层自己去拼 context
- 会导致 Motivation 层重复读取 `main.data`
- 会破坏 Contract 的"单一 Source of Truth"原则

**结论**：Context Foundation 是**低风险、高价值、被所有后续阶段依赖**的第一步。
